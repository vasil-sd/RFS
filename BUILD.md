# RFS Build, Test, and Run Instructions

**All build/run/test how-to for the RFS project lives here.** Toolchain locations,
versions, activation env vars, and reinstall procedure: see `TOOLCHAIN.md`.

## 1. Where the main build files are

| File | Role |
|---|---|
| `Cargo.toml` | WORKSPACE ROOT (Phase 5 task 1): `[workspace] members = ["crates/rfs-build", "crates/rfs-adapters", "crates/examples/sync_handler", "crates/examples/async_handler", "crates/examples/fuzz_rust"]` (explicit list - `crates/examples` itself has no manifest, and the Phase 5 task 12 C example projects are Makefile-driven and NOT cargo members) + the root package `rfs` v1.0.0 (edition 2021; lib + CLI (`src/main.rs`) + bins in `src/bin/`). Key deps: `nom` (+ optional `z3` under the `smt` feature); dev-deps `chumsky` (comparison tests only) + `comrak` 0.55 / `mermaid-rs-renderer` 0.3 (the mdr parser stack behind the doc-quality gate, Phase 6 task 7 rule change). The root package is an implicit workspace member. |
| `crates/rfs-build/` | `rfs-build` crate (Phase 5 task 1): the build.rs helper that invokes the `rfs` toolchain to generate protocol code at build time (`RFS_BIN` override, cargo rerun directives). Dependency-free. Builder options: `.backend()`, `.production()`, `.test_command()` (task 12, selects the `test` codegen command - the libfuzzer skeleton is written next to the main artifact as `fuzz_target.rs`/`fuzz_target.c`), `.with_property_monitors(bool)`, `.no_std(bool)` (task 9, maps to the production-only `--no-std` flag), `.with_protocol_fsm(bool)` (task 11, maps to `--with-protocol-fsm`). How consumers pull the generated artifact into their crate: see the `crates/examples/*` row (the `include!` + inner-attribute-stripping pattern). |
| `crates/rfs-adapters/` | `rfs-adapters` crate (Phase 5 task 11): the Rust-ecosystem integration layer - the `ProtocolFsm` trait + four generic adapters (sync channel, futures stream, callback driver, no_std-minimal wrapper). `#![no_std]` core with `std` (default) / `async` features; the only external dep is `futures` (optional, `async` feature) - it never leaks into the `rfs` toolchain or generated code. Never depends on generated code. |
| `crates/examples/sync_handler/`, `crates/examples/async_handler/` | Example crates (Phase 5 task 11): drive the spec-43 sliding-window ARQ sender end to end - sync over std mpsc channels (`ChannelFsm`), async as a futures Stream (`AsyncFsm`). build.rs generates the FSM via rfs-build with `--with-protocol-fsm`; the artifact is pulled in via `include!` of an OUT_DIR body file (build.rs strips the inner attributes, which `include!` rejects; the module-level `#[allow]` mirrors the artifact header). Each crate carries its session as a test (`cargo test -p <crate>`) plus a demo binary (`cargo run -p <crate>`, exit 0 on success). |
| `crates/examples/c_sync_handler/`, `crates/examples/fuzz_c/` (Makefile-driven, NOT cargo members), `crates/examples/fuzz_rust/` | Example projects (Phase 5 task 12): c_sync_handler = the C mirror of sync_handler on the generated spec-43 FSM (`gcc -Wall`, scenario data lines byte-identical to the Rust side); fuzz_c = clang+libFuzzer harness for the emitted `fuzz_target.c` (generation works without clang; building needs it); fuzz_rust = cargo-fuzz layout wiring the emitted libfuzzer_sys skeleton (root crate holds the generated production FSM; `fuzz/` is a DETACHED workspace; the adapted skeleton is gitignored and regenerated by build.rs via rfs-build's `.test_command()`). |
| `.cargo/config.toml` | Cargo aliases used throughout the docs (see section 4). Re-verified working after the workspace conversion (section 4 note). |
| `Cargo.lock` | Version 4 lock file - requires a recent cargo; use the project toolchain (`TOOLCHAIN.md`). |
| `src/` | Library + CLI source (map in `KB.md` section 4.2). |
| `tests/` | Integration test suites (layout in section 3 below). |
| `ide/` | IDE support (Phase 5 task 13): TextMate grammar for `.rfs` (`textmate/rfs.json`, scope `source.rfs`), snippet set (`snippets.rfs`), install notes for VS Code + Sublime (`README.md`). The parser's keyword list (`KEYWORDS` in `src/parser.rs`) is the shared source of truth - a test asserts every keyword appears in the grammar. |
| `target/rfs_codegen_tests/` | Generated aggregate unit-test crate (written by `cargo generate-code-tests`; not checked in). Its manifest carries an empty `[workspace]` table so cargo does not walk up into this repository's workspace. |

## 2. Activate the toolchain, then build

```sh
export RUSTUP_HOME=/workspace/host/rustup
export CARGO_HOME=/workspace/host/.cargo
export PATH="$CARGO_HOME/bin:$PATH"
cd /workspace/host/RFS

cargo build        # library + CLI + bins
cargo test         # full root-package suite (see section 3)
cargo test --workspace   # ALL members (root package + crates/*) - use this for a full check
```

Re-export the three env vars in **every** shell command that needs cargo (env does not
persist between tool calls). If `cargo --version` is not 1.99.0, see `TOOLCHAIN.md`.

Workspace note (Phase 5 task 1): with a root package present, plain `cargo build` /
`cargo test` / `cargo clippy` from the repo root select ONLY the root package (`rfs`) -
add `--workspace` (or `-p rfs-build` / `-p rfs-adapters` / `-p sync_handler` /
`-p async_handler`) to cover the helper + example crates. `cargo run` keeps working via
`default-run = "rfs"`, and every alias in `.cargo/config.toml` was re-verified after the
conversion (section 4).

SMT mode (Phase 4 task 11, optional, feature-gated) additionally requires the
project-local z3 install: activation env vars per `TOOLCHAIN.md` section 5.2
(`PATH=/workspace/host/z3/bin:$PATH` + `Z3_LIBRARY_PATH_OVERRIDE`); generated C
SMT output compiles per section 5.3.

## 6. Toolchain fuzzing (Phase 6 task 5, D-P6-4)

Fuzzes the TOOLCHAIN itself (distinct from Phase 5's `rfs test --suite fuzz`,
which fuzzes GENERATED code). Two layers:

| Layer | Where | What | When it runs |
|---|---|---|---|
| Fast: in-process libFuzzer targets | root `fuzz/` cargo-fuzz workspace (detached; 4 targets: `parser`, `validator`, `ir_roundtrip`, `codegen`) | no panic on malformed-but-parseable input; JSON round-trip byte-stability; total codegen + structural invariants (task-2 header, balanced delimiters, no placeholder tokens, core symbols) | manual / nightly (`cargo +nightly fuzz run <target> -- -max_total_time=...`) |
| Slow: seeded compile-and-run suite | `tests/toolchain_fuzz_test.rs` (part of plain `cargo test`) | 3 pinned seeds x 10 small specgen specs -> all six artifacts generated + compiled (rustc / gcc -Wall) + MC runs in exact & fuzz mode vs `ref_mc` ground truth: status agreement, NO false `PASS (complete)`, exit codes {0,1,2}, stable stderr; plus the deterministic trigger-step-0 report pin | every full test run (~30 s) |

Random specs are built through `src/specgen.rs` (seed + bounds from fuzzer bytes;
validity by construction - raw IR types are deliberately NOT `Arbitrary`).
Requirements: nightly toolchain + clang (TOOLCHAIN.md sections 7 / 7.5); the
harness works OFFLINE (`libfuzzer-sys 0.4.13` + `arbitrary 1.5.0` are cached).
Bounded smoke gate (availability-gated, never a hard failure when tools are
absent - same pattern as the e2e fuzz tests): `cd fuzz && cargo +nightly fuzz run
codegen -- -max_total_time=10` (the slowest target; the others are faster).

## 7. Benchmarks in CI (Phase 6 task 6)

The benchmark MC suite is a single command. It is also part of plain `cargo
test`, so any full CI run already covers it; run it standalone to get just the
benchmark signal plus its report:

    cargo test --test benchmark_mc_test

Requirements: the pinned toolchain (section 2 - rustc/cargo 1.99.0) + `gcc` at
`/usr/bin/gcc` (preinstalled on GitHub's ubuntu runners). Local wall-clock ~15 s.

**What it writes.** `target/mc_benchmarks.json` (development artifact - under
`target/`, never checked in): per spec x backend the status, deterministic
metrics (`states` / `transitions` / `max_depth` / `monitors_bits` /
`unexpected_terminations` / `memory_estimate_bytes`), `peak_rss_kb` (from the
binary's own JSON report; 0 on read failure) and `wall_ms` - plus a
`codegen_timing` section with in-process `parse_ms` / `codegen_ms` for the eight
timed specs (classic examples 03/04 + the six benchmarks).

**What it prints.** Two tables to the test output: the per-backend MC table
(spec, backend, status, states, transitions, max_depth, wall_ms, peak_rss_kb)
and the parse + codegen timing table.

**Asserted vs informational.** Asserted: pass-complete status on all six specs;
the pinned deterministic metrics (exact-mode counts are a pure function of the
spec - equality IS the bound); every FAIL variant's reason / label / step /
metrics / violation_step / cycle_length and its `ce_steps` from the JSON report;
field-identical results across backends on every run; byte-identical stdout for
`--threads 1/2/4` (and across backends) on all eight gate workloads; generated C
warning-free under `gcc -Wall`. Informational only - never asserted, except the
order-of-magnitude bound `peak_rss_kb < 1_000_000`: wall-clock times, parse/
codegen timings, and peak RSS values. CI machines vary, and these must not
become flaky gates (Phase 4 discipline).

**GitHub Actions** (documented only - no workflow file is committed in this
environment; the suite needs nothing beyond the toolchain + gcc):

```yaml
name: benchmark-mc

on:
  push:
  pull_request:

jobs:
  benchmark-mc:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Install the pinned toolchain (BUILD.md section 2)
        uses: dtolnay/rust-toolchain@1.99.0
      - name: Run the benchmark MC suite (single command)
        run: cargo test --test benchmark_mc_test
      - name: Upload the JSON report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: mc-benchmarks
          path: target/mc_benchmarks.json
```

(Timing/RSS values in the artifact are per-machine; compare trends, not
absolute numbers.)
