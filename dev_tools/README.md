# dev_tools - RFS maintenance tooling (Phase 12)

Workspace-member crate, binary `rfs-dev`: the routine maintenance operations
an LLM assistant otherwise performs by hand with shell commands - sources and
docs manipulation, context gathering, reference re-syncing. Dependency set is
a subset of the RFS project's dependencies plus exactly two declared
exceptions: `syn` (Rust-source parsing) and `pulldown-cmark` (Markdown
parsing). Nothing in the `rfs` build/test path invokes this crate.

## Analysis of tool calls patterns

Evidence base for the proposed tools: a systematic classification of ALL 12,596 assistant tool calls recorded in `commands.md` (the Phases 0-11 session log). Produced by `dev_tools/analysis/extract_calls.py` (inventory) + `classify_calls.py` (four-mode classifier); the per-kind TSVs under `dev_tools/analysis/` are the machine-readable source of this section - every count and abstract pattern below is transcribed from them, no manual numbers. FROZEN after Phase 12 task 3.5: later edits require a plan correction; a `dev_tools/PROTOCOL.md` re-run regenerates the section from fresh TSVs.

### What this means for the tool set

The operation classes that become tools are exactly the mechanical, repeated, token-expensive or error-prone ones: chunked file-content lookup (5,536 calls - 44% of all terminal calls) becomes `doc-section` + `context`; pattern-fragile rewrites (229 python bulk-rewrite + 32 shell-edit + the sources-modify/edit_file share they serve) become the syn-based `edit-*` trio; docs<->source reference re-syncing (the docs-modify class after any refactor) becomes `sync-check`/`sync-fix`; inventory table surgery + the string-masked audit (170 transform + 68 audit-mask python calls, plus the edit_file inventory rows) become `inventory add/update/remove/audit`; and the analysis pipeline itself (this section's extraction + classification) becomes `calls extract/classify` so that a PROTOCOL.md re-run on a new commands.md is one command pair. The classes that do NOT become tools, with reasons: build/test execution and git (the real tools already exist), env-check and vendored-deps lookup (per-sandbox liveness / per-version staleness), file-ops residual and scratch edits (heterogeneous), new-file creation of docs or sources (design work, template-governed), json-processing/orchestration/analysis (task-specific judgment), and the two misc kinds (platform capability / external one-off).

### No-tool decisions (classes failing a criterion, with reasons)

- build-test-run (2,126): cargo IS the build/test tool - wrapping it would duplicate its UX.
- git (583): the system of record; a wrapper adds no determinism.
- env-check (207): per-sandbox liveness - probing must stay live.
- lookup-vendored-deps (125): external crate sources change with dependency versions; a cached index would go stale.
- shell-write (182) and docs-new (225): template-governed creation (FORMATTING.md templates + review), not generator territory this phase.
- sources-new (91): new-file creation is design work, not a mechanical operation.
- file-ops residual (47): `edit-move` covers the repo-relevant subset; raw scratch mv/rm/cp stay manual.
- other-terminal (703) and other-edit_file (24): heterogeneous residual / session-local scratch.
- json-processing (51), orchestration (26), analysis (274): task-specific judgment - the one recurring JSON case (the commands.md inventory) is covered by `calls extract`.
- conversation-recall (83): a platform capability no repo tool can replace.
- web-docs-lookup (34): external and one-off per dependency - fails the mechanical-repeated criterion.

### DOCS_STRUCTURE.md decision: REJECTED for this phase

Decided from the frozen data, per the rule in PHASE_12_TASK_4.md: build the
section-level docs inventory only if lookup-docs calls show frequent
cross-file section hunting. They do not - of the 2,035 lookup-docs calls,
only 17.2% mention two or more distinct doc files in one command, and those
are directory listings (`ls`), size checks (`wc -c`) and cross-document
reference greps, NOT heading-name hunts across files. The dominant patterns
are single-file range reads against already-known line numbers (32.5%) and
intra-file heading greps to OBTAIN line numbers (13.2%) - the token-economy
protocol of START.md section 0, where the assistant already knows the target
file from TASK_MAP/CHANGE_IMPACT. `doc-section`'s on-the-fly pulldown-cmark
heading walk plus its `all` mode covers the observed need without a prebuilt
index that would itself need re-syncing (adding sync-check surface for no
measured benefit). Revisit under `dev_tools/PROTOCOL.md` if a future
commands.md shows frequent cross-doc heading hunts.
