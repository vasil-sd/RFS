## Context

Review of `PHASE_6.md` (frozen phase description) against the shipped state after
Phase 5 close-out (2026-10-23). Findings that shape this plan:

- **Version header ALREADY EXISTS**: the parser accepts an optional module-level
  `version "x.y.z"` header (any quoted string; `src/parser.rs` ~line 235), it is stored
  in the IR (`Module.version`), round-tripped by the printer, and shown by `rfs info`
  (`(version v)`). There is NO format validation. The invalid example
  `invalid_bad_version_header.rfs` pins the unquoted form as a parse error.
  Decision D-P6-1: formalize THIS existing mechanism as the v1.0 syntax version header
  (add a validator format check) instead of adding PHASE_6.md's illustrative
  `# rfs 1.0` comment syntax - two parallel mechanisms would be ambiguous, and the
  existing one is IR-stored and visible to every tool.
- **IR schema version**: `IR_VERSION = 0` (`src/ir.rs:28`); `from_json` accepts ANY
  uint (no compatibility check). Decision D-P6-2: bump to 1 for v1.0, accept
  {0, 1} on read (current + all previous minor versions), write 1; document the policy.
- **Generated code carries NO spec hash / toolchain version**: Rust header is
  `// Generated by RFS Phase 1 codegen.` (`src/backends/rust_fsm.rs:174`), C header
  `// Generated by RFS Phase 3 codegen (C backend). Do not edit.`
  (`src/backends/c_fsm.rs:395`); fuzz-skeleton headers in `rust_test.rs`/`c_test.rs`.
  Crate version is 0.1.0; the `--print-script` header already embeds
  `env!("CARGO_PKG_VERSION")` (`src/ext_tool.rs:327`). Decision D-P6-3: hand-rolled
  minimal SHA-256 in a new `src/spec_hash.rs` (no new dependencies - consistent with
  the D-P5-2 hand-rolled-JSON stance), hashing the CANONICAL IR JSON bytes
  (deterministic key order per D-P5-2); every generated artifact of both backends gets
  a header line with toolchain version + first 16 hex chars of the spec hash; crate
  version bumps to 1.0.0.
- **Existing soundness infrastructure to build on** (do not duplicate):
  `tests/backend_parity_test.rs` (Phase 4/5: exact-mode MC parity over ALL
  property-bearing examples - field-identical results + byte-identical JSON reports -
  and generated test-executable agreement incl. a byte-identical random-trace line);
  `tests/benchmark_mc_test.rs` (specs 43/44/45 x both backends, pinned deterministic
  metrics, FAIL variants with counterexample parity, `target/mc_benchmarks.json`,
  wall-clock INFORMATIONAL only); the reference interpreter in `src/monitor.rs`
  (toolchain-SIDE - Phase 6's hand-written references must be independent of it);
  the seeded LCG random-trace class in `codegen_test` (byte-pinned sequence family);
  the scenario-parity pattern in `example_projects_test` (C/Rust byte-identical data
  lines driven from identical input scripts).
- **Environment facts**: `cargo-fuzz` is installed; `clang` + `gcc` present;
  `libfuzzer-sys 0.4.13` + `arbitrary 1.5.0` are already cached in CARGO_HOME (a
  root-level cargo-fuzz workspace works OFFLINE); NO external PSL model checker exists
  here (no nuXmv/SPIN; z3 is SMT-only, not a PSL trace checker) - decision D-P6-8:
  independent in-repo trace evaluator + a documented availability-gated external hook;
  NO `.github/workflows` in this environment - decision D-P6-9: "benchmark suite runs
  in CI" = the standard verification pipeline (`cargo test --test benchmark_mc_test`,
  one command, JSON report + per-backend table) plus GitHub Actions wiring documented
  as a snippet in BUILD.md.
- **MC machinery facts**: generated MC binaries accept `--seed` (default 12345) and
  `--violate label:prob:percent%` forced-assumption-violation directives
  (`src/codegen_mc.rs`); exact mode is seedless and deterministic (D-P4-7); status
  taxonomy is PassComplete / Fail / UnknownStateLimit - UnknownStateLimit must NEVER be
  a completeness claim. This is the "no false `PASS (complete)`" invariant of Phase 6.
- **Byte-pin impact** (re-pins happen INSIDE the owning task): task 2.3's header change
  touches pins in `tests/codegen_test.rs` (~lines 1173/1243/1252/1311) and
  `tests/example_projects_test.rs` (~line 187); task 6.2's new JSON report field
  touches the D-P5-10 document-shape byte-pins + golden full-document pin (lib
  codegen_mc suite) and the parity-suite JSON agreement checks.
- **Exit criterion "production code generation is used in at least one real or
  realistic protocol project"**: the Phase 5 example-crate matrix
  (`sync_handler` / `async_handler` / `c_sync_handler` driving the spec-43
  sliding-window ARQ end to end via rfs-build + adapters, with session tests and demo
  binaries) satisfies it. Task 10 re-verifies all three projects green and records the
  satisfaction in `PHASE_6_STATUS.md`.
- **New example numbering**: task 2.1 adds `46_version_header.rfs` (valid) +
  `invalid_bad_version_format.rfs`; task 6.1 adds `47_http2_stream.rfs`,
  `48_usb_control_transfer.rfs`, `49_can_arbitration.rfs`. The examples_test count
  pins (currently 45 valid / 12 invalid) are re-pinned in the owning tasks (46/13
  after task 2, 49/13 after task 6).
- **Baseline to build on** (Phase 5 close-out): 376/376 main tests (400 with
  `--workspace`, 378 with `--features smt`), 1501/1501 generated-code tests (184
  modules), 45 valid + 12 invalid examples, training aggregate 244 lines
  (135 valid + 127 invalid snippets). New valid examples grow the aggregate crate -
  regenerate + re-pin where asserted.
- **User request (2026-10-23, plan review)**: (1) expose the reference brute-force MC to the USER as a CLI command - for rapid prototyping in shell/REPL without compiling a generated MC; its CLI flags unified with the code-generated MC where applicable; (2) expose the spec generator too, EXTENDED with incremental generation based on a given base spec (mutating a known base 'shape' gives much better corner-case coverage than fully random specs). Incorporated as extensions of subtasks 3.1/3.2 + new subtasks 3.3/3.4 and decisions D-P6-10/D-P6-11.

Planning decisions taken during this review (referenced by task rows; all of them
get a full entry in `DESIGN.md` section 24 during task 9):

- **D-P6-1**: the v1.0 syntax version header is the EXISTING module-level
  `version "x.y.z"` mechanism, formalized with a validator format check - no new
  comment-style header (task 2.1).
- **D-P6-2**: `IR_VERSION` bumps 0 -> 1; reads accept {0, 1} (current + previous
  minor versions stay loadable) (task 2.2).
- **D-P6-3**: every generated artifact carries toolchain version + spec hash
  (SHA-256 of canonical IR JSON, first 16 hex chars); hand-rolled SHA-256, no new
  dependencies; crate version -> 1.0.0 (task 2.3).
- **D-P6-4**: toolchain fuzzing is TWO layers - fast in-process libFuzzer targets in
  a root-level `fuzz/` cargo-fuzz workspace + a slow compile-and-run seeded
  deterministic suite that runs in CI (tasks 5.1/5.2).
- **D-P6-5**: the brute-force reference MC is a public lib module (`src/ref_mc.rs`)
  with deliberately different data structures and its own property evaluator - no
  shared code with the generated engines (task 3.2).
- **D-P6-6**: production-FSM cross-backend parity uses thin driver wrappers around
  the generated production code, driven by identical seeded input scripts,
  byte-identical stdout (task 4.3).
- **D-P6-7**: monitor references are HAND-WRITTEN independent Rust + C code inside
  the test suite for the benchmark specs' properties - not reusing `src/monitor.rs`
  (task 4.4).
- **D-P6-8**: PSL translation checks use an independent in-repo trace evaluator
  (different algorithm from `monitor.rs`) plus a documented availability-gated
  external-tool hook (`RFS_PSL_REF_TOOL`); no external PSL checker exists in this
  environment (task 4.5).
- **D-P6-9**: "benchmark suite runs in CI" = the standard verification pipeline
  (`cargo test --test benchmark_mc_test`, one command, JSON report + per-backend
  table) plus GitHub Actions wiring documented as a snippet in BUILD.md; no
  `.github/workflows` is committed (none exists in this environment) (task 6.3).
- **D-P6-10**: the reference MC is exposed as the `rfs mc-ref` command with FLAGS UNIFIED to the generated MC binary where applicable (`--max-states`, `--timeout-sec`, `--assumes`, `--counterexample-format json|text`, `--log-level`; exit codes 0 pass-complete / 1 fail / 2 unknown-state-limit mirrored); fuzz-mode-only flags (`--seed`, `--steps`, `--violate`) do not apply - ref_mc is exact exhaustive search only (D-P4-7: exact mode is seedless); the report format (text + JSON) is identical to the generated engines' so outputs are directly comparable (tasks 3.2/3.3).
- **D-P6-11**: the spec generator is exposed as the `rfs gen-spec` command with two modes - fully random (`--seed` + size bounds) and incremental mutation from a base spec (`--base SPEC --mutations K`); validity is preserved at every mutation step (invalid candidates rolled back + redrawn). Rationale (user request 2026-10-23): mutating a known base 'shape' gives much better corner-case coverage than fully random specs (tasks 3.1/3.4).
