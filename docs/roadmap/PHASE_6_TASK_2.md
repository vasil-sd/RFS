# Phase 6, Task 2 - Implementation details

> Written for a future LLM session: after reading `START.md`,
> `docs/roadmap/INTRO.md` and this file, the assistant must be able to start
> implementation of the task immediately without re-deriving scope.

## Goal
Define the v1.0 stability surface (decisions D-P6-1..3): formalize the RFS syntax
version header, bump the IR schema version 0 -> 1 with a documented compatibility
policy, and put the spec hash + toolchain version into EVERY generated artifact
(both backends, all commands) - plus the crate version bump to 1.0.0 and the
generated-code compatibility policy / migration guide process document.

## Context

- **Version header (D-P6-1)**: the parser ALREADY accepts an optional
  module-level `version "x.y.z"` header (any quoted string; `src/parser.rs`
  ~line 235, keyword at line 45). It is stored in `Module.version`, round-tripped
  by `src/printer.rs` (~line 41), and shown by `rfs info` (`(version v)`,
  `src/info.rs` ~line 235). There is NO format validation today. The invalid
  example `examples/invalid/invalid_bad_version_header.rfs` pins the UNQUOTED
  form as a parse error (keep it - still correct). Decision: formalize THIS
  mechanism; do NOT add PHASE_6.md's illustrative `# rfs 1.0` comment syntax.
- **IR version (D-P6-2)**: `IR_VERSION: u32 = 0` at `src/ir.rs:28`; `from_json`
  (~line 449) accepts ANY uint - no compatibility check. Golden JSON pins with
  `"ir_version":0` live in `tests/frontend_test.rs` (~lines 713, 724) plus the
  lib round-trip tests (grep `ir_version` in `src/lib.rs` tests / `src/ir.rs`
  tests - one pins `ir.ir_version == 0`).
- **Generated headers (D-P6-3)**: Rust line 1 = `// Generated by RFS Phase 1
  codegen.` (`src/backends/rust_fsm.rs:174`); C line 1 = `// Generated by RFS
  Phase 3 codegen (C backend). Do not edit.` (`src/backends/c_fsm.rs:395`);
  fuzz-skeleton headers in `src/backends/rust_test.rs:679` and
  `src/backends/c_test.rs:551`. Header pins to re-pin: `tests/codegen_test.rs`
  ~1173 (`starts_with("// Generated by RFS Phase 1 codegen.\n#![no_std]\n")`),
  ~1243 (`std_lines[0] == "// Generated by RFS Phase 1 codegen."`), ~1252
  (`expected_header` vec first entry), ~1311 (`l.starts_with("// Generated by
  RFS")` - stays true, verify); `tests/example_projects_test.rs` ~187 (C header
  `starts_with`). The `--print-script` header embeds `env!("CARGO_PKG_VERSION")`
  (`src/ext_tool.rs:327`) and is BYTE-PINNED with `rfs 0.1.0` in lib tests
  (`src/ext_tool.rs` ~489/499/569) and `tests/frontend_test.rs` (~1962, ~2041)
  - the crate bump re-pins those to `rfs 1.0.0`.
- **Canonical IR JSON**: `Ir::to_json()` via the hand-rolled writer (`src/json_rw.rs`,
  D-P5-2) has deterministic key order and formatting - it is a stable hash input.
  The spec hash covers the WHOLE input file (all modules), one hash per artifact;
  document this in MIGRATION.md (multi-module behavior: verify how codegen selects
  modules for `30_multi_module.rfs` and state it).
- **No new dependencies** for hashing (project stance, D-P5-2): hand-rolled
  minimal SHA-256.
- Execution order note: this task runs BEFORE tasks 4-6 so all new suites see the
  final header format; do the full re-pin sweep HERE in one pass.

## Planned actions

### Action 1: syntax version header formalization (subtask 2.1)
Add a VALIDATOR check: if `Module.version` is present it must match
`^\d+\.\d+(\.\d+)?$`; otherwise emit a semantic error with a pinned message
(e.g. `module 'm': invalid version header "1.x" (expected X.Y or X.Y.Z)` -
decide the exact wording and pin it). The parser keeps accepting any quoted
string (old files still PARSE; validation rejects bad formats) - this keeps the
parse/validate split consistent with existing semantic errors. Add
`examples/valid/46_version_header.rfs` (a small spec, `version "1.0"`) and
`examples/invalid/invalid_bad_version_format.rfs` (`version "1.x"`). Re-pin
`tests/examples_test.rs` counts to 46 valid / 13 invalid. Lib validator tests:
valid formats accepted (`1.0`, `1.2.3`), malformed rejected with the pinned
message, absent header still accepted (legacy).

### Action 3: spec hash module (subtask 2.3a)
New `src/spec_hash.rs`: hand-rolled SHA-256 (standard FIPS 180-4 algorithm,
~100 lines, no dependencies) with API `pub fn sha256_hex(data: &[u8]) -> String`
(full lowercase hex) and `pub fn spec_hash16(canonical_ir_json: &str) -> String`
(first 16 hex chars). Unit tests with NIST vectors (at minimum: empty string,
`"abc"`, and one multi-block vector e.g. the two-80-char message from the FIPS
test suite). Register `pub mod spec_hash;` in `src/lib.rs`.

### Action 4: header change on all artifacts (subtask 2.3b)
In `src/codegen.rs`: compute the spec hash from the canonical IR JSON of the
INPUT FILE (`ir.to_json()` rendered text - deterministic per D-P5-2) once per
codegen invocation and pass it to the backends (extend `BackendOptions` or the
generation entry points). New LINE 1 for every generated artifact, BOTH
backends, all three commands + fuzz skeletons (unified text - parity):

```text
// Generated by RFS v{CARGO_PKG_VERSION} | spec sha256:{hash16} | module {module_name}
```

Line 2 onward stays UNCHANGED (the `#![allow(...)]` / C comment block etc.).
Fuzz skeletons get the same line 1 (they are extra files of the `test` command).
Then the full re-pin sweep: `tests/codegen_test.rs` (~1173/1243/1252 - update to
the new format; ~1311 verify), `tests/example_projects_test.rs` (~187), and any
other assertion touching line 1 (grep `Generated by RFS` across tests/). The
hash in pins: use a FIXED spec (e.g. example 01) and compute its expected hash16
once, then pin the literal (deterministic - canonical JSON is stable).
